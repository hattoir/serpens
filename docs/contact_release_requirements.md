## 2. 物理の側で先に確かめること（HARDWARE_UNVERIFIED）

- **STS3215-C044 のギア比は 1:191。** 脱力しても外から関節を回すのに要るトルク（バックドライブ）が
  **未測定（UNKNOWN）**。高減速比のサーボは脱力しても「固いまま」のことがあり、
  その場合 TORQUE_DISABLE は挟まれた指を解放しない。**脱力が解放になる前提を置かない。**
- 挟み込みを解くには「逆に少し動かす（後退）」が要るかもしれない。これは能動動作なので、
  誤検知時の危険と天秤になる（Q3）。
- J7（首ピッチ）は脱力で頭が落下する。対象から外すか、保持にするかを決める（Q4）。

## 3. 20ms の時間予算（計算値。実測ではない）

1M bps・8N1 では 1 バイト ≈ 0.01ms（`docs/sts3215_registers.md` の通信仕様から計算）。

| 区間 | 見積もり | 根拠 / 未確定 |
|---|---|---|
| 負荷の読み出し（SYNC READ 0x38 から 8 バイト × 9 軸） | 要求 17 + 応答 14×9 = 143 バイト ≈ **1.4ms** + 応答遅延 | 応答遅延（番地 7）の実値は **UNKNOWN**。SYNC READ 非対応なら個別 READ で約 9 倍の往復 |
| 判定（しきい値・連続回数） | 制御周期 10ms × **k 回** | k=1 だと誤検知に弱い（Q6）。k=2 で **最悪 20ms を使い切る** |
| 脱力の書き込み（SYNC WRITE 番地 40 × 9 軸） | 26 バイト ≈ **0.3ms** | 応答なし |
| サーボ内部で出力が落ちるまで | **UNKNOWN** | データシートに記載なし |
| 力が実際に抜けるまで | **UNKNOWN** | §2 のバックドライブ次第 |

読み方: **通信だけなら 20ms に収まる計算になるが、判定の連続回数を 2 回にした時点で余裕が無い。**
PC を経由すると、テレメトリ 10Hz（100ms）と USB 往復が乗るので**原理的に届かない**。

## 4. 設計案 — 機体（ESP32）側で閉じる

```
100Hz 制御周期（firmware の control()）
  readServos()                       ← 負荷・位置を読む（いまは空関数）
  contactCheck()                     ← 新設。PC の判断を待たない
     |load| > contact_load_ratio を k 周期連続     （Q2・Q6 が決まるまで値は置かない）
     or |目標 − 実測| > contact_pos_err_deg を k 周期連続
  → 反応（Q3 で決める）: HOLD or TORQUE_DISABLED
  → EVENT を PC へ通知（通知は後。止めるのが先）
  writeServos()                      ← 反応後の出力
```

- **ラッチ扱いにする**: 接触での停止は `EMERGENCY_LATCHED` と同じく、原因が消えても自動復帰しない。
  CLEAR_FAULT → DISARMED → 明示 ARM の段差を保つ（`CLAUDE.md` の安全設計）。
- 設定は `link.faults` に置き、**ファームと Python の値の一致を `tests/test_firmware_sync.py` で検査**する。
- 仮想機体（`serpens/link/device.py` の `_watchdogs`）に同じ判定を足せば、PC が止まっていても
  脱力することを SIMULATED で試験できる。ただし**しきい値は実測が無いと決められない**ので、
  現時点では実装しない（無意味な既定値でスイッチだけ作ると「実装済み」に見えるため）。

## 5. 実装に進む条件

1. Q1〜Q5 が決まっている（製品・機構の判断）
2. 実サーボで、歩容中の負荷分布と、指を模した荷重をかけたときの負荷を測ってある（Q6）
3. 脱力時のバックドライブトルクを測ってある（§2）
4. `ELECTRICAL_SAFETY_GATE`（`docs/safety_limits.md` §5）の「実停止時間」が測れる環境がある

それまでは PC 側の 800ms の経路が唯一の経路であり、**`contact_release_ms: 20` は未達のまま表示する。**
